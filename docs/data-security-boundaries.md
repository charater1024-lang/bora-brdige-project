# 데이터·암호화·DB 보안의 적용 범위

이 문서는 2026-09-27 공개용 v0.8.11 후보 소스의 구현을 읽고 관련 테스트를 확인한 기록입니다. 실제 운영 서버·회원 DB·Windows 백업 폴더에는 접근하지 않았습니다. **소스 공개 검사 통과는 코드의 무결점, DB 전체 암호화, 운영 환경의 안전을 보증하지 않습니다.** [미해결 라이브러리 경고](public-source-publication.md#해결-전-의존성-보안-경고)도 별도로 남아 있습니다.

## 구현으로 확인한 보호

| 대상 | 확인한 처리 | 보호 범위의 한계 |
| --- | --- | --- |
| 관리 화면에서 DB에 저장하는 API 키 | AES-GCM, 매 저장마다 무작위 12바이트 IV, 키 이름을 추가 인증 데이터로 사용 | 환경의 암호화 키가 필요하며, 환경파일 자체를 암호화하지는 않음. 확인용 마지막 4글자는 별도 필드 |
| 로그인 세션 | 32바이트 난수 토큰, DB에는 SHA-256 해시, 만료 검사 | 원본 토큰 해시 저장이지 세션 테이블 전체 암호화가 아님 |
| 자산·프로필·회원 데이터 | 인증된 사용자 ID를 기준으로 조회·저장, SQL 값 바인딩 | 일반 TEXT/JSON 필드이며 애플리케이션 수준의 전체 DB/필드 암호화는 아님 |
| 주요 상태 변경 API | 동일 출처 검사, 인증·관리자 권한 검사 | 모든 공격 경로를 검증했다는 의미는 아니며 서버 권한이 탈취되면 앱 통제도 우회될 수 있음 |
| 암호화 백업 경로 | AES-256-GCM으로 내용 암호화, RSA-OAEP-SHA256으로 데이터 키 보호, 무결성·복원 검사 | 아래 직접 실행 방식과 실제 운영 설정에 따라 암호화 여부가 달라짐 |
| Windows 백업 복구 키 | Windows CurrentUser DPAPI로 개인키 보호, 서버에는 공개키만 제공하는 구조 | Windows 사용자·기기 복구 및 별도 키 복구 계획 필요. DPAPI만으로 폴더의 모든 내용을 보호하지는 않음 |

근거: [API 키 저장](../lib/runtime-settings.ts), [세션 저장](../lib/auth/store.ts), [자산 저장](../lib/manual-finance-store.ts), [DB 구조](../db/schema.ts), [백업 도구](../deploy/backup-bora-sqlite.py), [Windows 클라이언트](../deploy/windows-backup-client.py).

API 키 암호화 환경 키가 없거나 32자 미만이면 관리 화면의 키 저장을 거부합니다. 복호화 실패한 암호문을 평문 키로 사용하지는 않으며, 별도로 설정된 환경변수 자격증명을 사용할 수 있습니다. 길이 검사는 키의 충분한 무작위성을 보증하지 않으므로 운영자가 강한 난수 키를 별도 생성·보관해야 합니다. DB를 복원해도 이 암호화 키가 없으면 저장된 API 키를 복원할 수 없습니다.

## 알려진 운영 도구 한계 — 미수정

### Windows 기존 백업 폴더의 접근 권한

`deploy/windows-backup-client.py`의 `secure_directory()`는 기존 폴더를 허용하고 `icacls /inheritance:r /grant:r`로 권한을 설정합니다. 이 처리만으로는 다른 사용자에게 이미 부여된 **명시적 허용 권한**을 모두 제거하거나 부재를 검증하지 못합니다. 따라서 코드 주석의 “현재 사용자와 SYSTEM만 접근”이라는 조건을 모든 기존 폴더에서 보장하지 못합니다.

명령의 권한 상속·특정 사용자 권한 변경 범위는 [Microsoft의 icacls 설명](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/icacls)을 참고하세요. 이 한계는 실제 정보 유출을 확인했다는 의미가 아닙니다.

실제 PC의 ACL은 이번에 조사하지 않았으며 데이터 노출을 재현한 결과도 아닙니다. 복원 검사에서는 일시적으로 평문 SQLite 파일을 만들므로 Python 버전과 임시 폴더의 실제 권한도 함께 확인해야 합니다. **이 사본의 Windows 백업 도구를 실제 회원 DB에 사용하기 전에 권한 처리 보완과 ACL 검증이 필요합니다.** 암호화 백업 파일 자체의 암호화와 로컬 복원 과정의 접근 통제는 서로 다른 보호입니다.

### 백업 도구의 평문 실행 방식

예약 실행용 샌드박스 스크립트는 백업 공개키가 없으면 중단합니다. 그러나 `deploy/backup-bora-sqlite.py`를 직접 공개키 없이 실행하는 방식은 평문 SQLite 백업을 만들 수 있습니다. 따라서 “백업 도구가 있으니 모든 백업이 자동 암호화된다”고 가정해서는 안 됩니다. 실제 명령·설정·생성 파일의 암호화 여부를 확인해야 합니다.

## 이번 공개 점검으로 확인하지 않은 것

- 운영 디스크/스토리지의 저장 시 암호화, 실제 DB·설정 파일 권한
- 운영 서비스 계정 격리, 방화벽·HTTPS·프록시 설정의 현재 상태
- 암호화 키의 무작위성, 비밀관리·회전·복구 체계
- 실제 Windows 폴더와 복원 임시 폴더의 ACL
- 예약 백업의 현재 활성화 상태, 최신 백업의 실제 복원 성공
- 현재 서버의 침해 여부, 모든 권한 우회 경로, 완전한 침투 테스트

사용자별 접근 분리는 애플리케이션에서 구현한 통제이며 DB 자체의 사용자별 권한 또는 RLS 보장은 아닙니다. 서버 프로세스는 필요한 DB 접근 및 키 복호화 권한을 가지므로, 서버 코드 실행 취약점은 암호화만으로 막을 수 없습니다.

실제 배포 전에는 알려진 의존성 및 운영 도구 문제를 보완하고, 별도의 비운영 DB로 권한·세션·백업/복원·기능 회귀를 검증해야 합니다. 이 공개 작업에서는 운영 파일·DB·백업·키·서비스를 변경하지 않습니다.
